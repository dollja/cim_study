How to fill the human review JSON

15 fields, 20 case IDs, and a practical handoff to the pilot workflow.

Read evidence in the HTML; write your own judgment in the matching JSON record. The HTML is a static workbook and does not save or synchronize JSON. This reference explains the attached files and supplies optional language. It does not adjudicate any case or report new model runs.

3. Short instructions and example for every field

Keep field names and case IDs unchanged. JSON strings need double quotes; true, false and null do not. [] is an empty list; null is unfilled or undecided, not a completed negative judgment. The template is not a formal JSON Schema: the nested examples below are recommended conventions. Coordinate these conventions with the other reviewer.

1. review_status

Type: string. Where: Your review process; the HTML status caption is static.

Track your own progress. Keep unreviewed until started; use a documented in_progress convention while evidence fields are unfinished; use reviewed after completing the individual judgment. Adjudication is a later step.

{
  "review_status": "in_progress"
}

Use this example when: Suggested workflow convention, not an enum enforced by the attached template.

2. reviewer_id

Type: string or null. Where: Your identity, not a dialogue speaker.

Enter a consistent reviewer code in quotation marks. Keep each reviewer’s file separate.

{
  "reviewer_id": "r1"
}

Use this example when: Use the code actually assigned to you.

3. prefix_first_review_completed

Type: boolean. Where: Your actual reading and recording sequence.

Record whether you completed the first judgment using the admitted prefix/context before opening the assistant interpretation and later turns. This flag alone does not establish blindness.

{
  "prefix_first_review_completed": true
}

Use this example when: Only if that sequence really occurred; prior exposure must also be recorded.

4. assistant_draft_seen_before_judgment

Type: boolean or null. Where: Your exposure history, including interpretation-bearing titles.

Record whether you had already seen case-specific draft interpretations. For this simple form, conservatively record true for advance exposure to the HTML’s interpretive titles and explain that exposure in the reason field. Null means unrecorded, not no exposure.

{
  "assistant_draft_seen_before_judgment": true
}

Use this example when: Use true only when exposure happened; use false only when you can affirm it did not.

5. focal_pair

Type: array of two participant-ID strings, or null. Where: Complete observer prefix → Speaker column.

Name the two speakers being compared. Use their actual IDs. Participant A/B in the draft are not a fixed giver/follower order.

{
  "focal_pair": [
    "giver",
    "follower"
  ]
}

Use this example when: Suitable for a giver/follower comparison; WW02 could instead use Justin and Dan.

6. local_question

Type: string or null. Where: Derive from the prefix; later compare with draft Local question.

Write one bounded question about the same event or subtask for both speakers. Do not ask about the whole dialogue when judging one exchange.

{
  "local_question": "On which side of the pine should the current route segment pass?"
}

Use this example when: An illustrative MT03 question, subject to your own choice of focus and referent review.

7. focus_source_ids

Type: array of strings. Where: Complete observer prefix → ID column.

Copy exact IDs for the focal exchange, preserving zeros and conversation identity. Cite earlier antecedents or corrections inside the supporting evidence. Nothing may exceed the case cutoff.

{
  "focus_source_ids": [
    "q1ec4.row.018",
    "q1ec4.row.019"
  ]
}

Use this example when: An illustrative MT03 focal pair of turns; the full prefix remains available and is not truncated to these IDs.

8. participant_meanings_with_source_quotes

Type: array of evidence objects (recommended shape). Where: Prefix wording and admitted context; draft Participant A/B only after your first judgment.

For each person, separate your interpretation from exact source quotations. Record the turn ID for each quote. Distinguish an instruction, question, acknowledgment, correction, and endorsement.

{
  "participant_meanings_with_source_quotes": [
    {
      "participant_id": "follower",
      "meaning": "Repeats the giver’s above relation; the referent of it still requires checking.",
      "source_quotes": [
        {
          "source_id": "q1ec4.row.019",
          "quote": "up above it"
        }
      ]
    }
  ]
}

Use this example when: One illustrative entry, not a complete two-person judgment. The nested keys are a proposed recording convention.

9. task_outputs

Type: object or null (recommended shape). Where: Your consequence comparison; draft Computed-output proposal is a later check.

Write the consequence implied by each supported reading, holding the question/event fixed. Mark conditions explicitly. A proposed route or accusation target is not proof that an action occurred or a hidden role is true.

{
  "task_outputs": {
    "giver": {
      "proposed_output": "Pass above the pine in this route segment."
    },
    "follower": {
      "proposed_output": "Pass above the pine in this route segment."
    },
    "conditions": [
      "Verify that it refers to the pine introduced at q1ec4.row.015.",
      "Verify the relevant map correspondence."
    ],
    "status": "conditional proposal; not an executed route or human-adjudicated result"
  }
}

Use this example when: Illustrative MT03 proposal only; retain uncertainty until the required checks are actually complete.

10. blocking_uncertainty

Type: boolean or null (recommended convention). Where: Your support/context checks; draft Uncertainty and Media review can prompt later checks.

Use true when a known open issue prevents a defensible comparison, false only after ruling out such blockers, and null before assessing it. Explain the issue in task_outputs conditions or the review reason.

{
  "blocking_uncertainty": true
}

Use this example when: For example, when a required pronoun link or map correspondence has not been verified.

11. provisional_label

Type: coded string or null. Where: Your prefix-based comparison; never copy a draft badge as an answer key.

Use ALIGNED, POTENTIAL_MISMATCH, or UNRESOLVED after doing the comparison. Use null while still unrated. Conditional badges displayed by the HTML are not extra standard label codes.

{
  "provisional_label": "UNRESOLVED"
}

Use this example when: Only when a completed analysis cannot establish the comparison. Unfinished annotation alone should remain null.

12. evidence_verified

Type: boolean or null (recommended convention). Where: Actual source checking, including any context needed by your judgment.

Set true only after the claimed quotations, source identity, support, and necessary context have been checked. Describe verification scope. Checking strings in the HTML alone does not verify the original transcript, maps, or semantic interpretation.

{
  "evidence_verified": null
}

Use this example when: Null while unassessed; false when known checks remain or fail; true only when the declared scope is complete.

13. include_in_pilot

Type: boolean or null. Where: Your inclusion recommendation after applying the study’s criteria.

Use true to recommend inclusion, false to recommend exclusion, and null while undecided. Inclusion is separate from the interpretation label. An unresolved case can be intentionally retained under a documented sampling plan.

{
  "include_in_pilot": null
}

Use this example when: Use null for a pending inclusion decision; this does not update pilot_selection.csv.

14. inclusion_or_exclusion_reason

Type: string or null. Where: Your evidence-based selection rationale; draft Why this case is only a suggestion.

Explain retain, defer, replace, or exclude using this case’s source IDs. Record any outstanding conditions or exposure limits. Do not reuse a sentence unless its factual premise fits the case.

{
  "inclusion_or_exclusion_reason": "Decision pending: q1ec3.row.012 explicitly reports no graveyard. Check the relevant maps and whether this missing-context case fits the sampling plan."
}

Use this example when: An illustrative MT02 rationale, not an inclusion decision or final classification.

15. later_evidence_review_completed

Type: boolean. Where: Separate curator_cases/FULL_CASE_ID.json; later turns are absent from this HTML.

Keep false until later evidence was actually reviewed. First preserve a dated copy of the prefix-only judgment. Put later-outcome notes in a separate record; this form has no dedicated outcome-note field.

{
  "later_evidence_review_completed": false
}

Use this example when: Correct while the later evidence has not yet been reviewed.

4. Choose a label only after comparing supported consequences

ValueMeaning
nullNo judgment entered yet. This is appropriate while the annotation itself is unfinished.
ALIGNEDFor the same question/event, each participant has the same single supported task output and no blocking uncertainty remains.
POTENTIAL_MISMATCHFor the same question/event, the supported consequence sets are nonempty and do not overlap, with no blocking uncertainty.
UNRESOLVEDA completed prefix-based analysis cannot establish the comparison because support, scope, necessary context or outputs remain indeterminate.

Unresolved does not mean excluded. Pending reviewer disagreement does not automatically make the episode UNRESOLVED. No discovered candidate is not automatically ALIGNED. The simple form has no dedicated no-candidate field: document that result explicitly in the reason and do not invent a focal comparison or force a label.

HTML badges such as ALIGNED_CONDITIONAL_ON_MAP_REVIEW and UNRESOLVED_OUTSIDE_STARTER_ADAPTER explain draft conditions. Do not paste them into the three-code label field as final outcomes. Local alignment also does not imply that the whole prefix is free of other mismatches.

6. A complete JSON structure, using fictional evidence

This invented two-turn example shows how all 15 fields can fit together. It is not a pilot case, and its hypothetical verification flags must not be transferred to real records. Both invented maps identify the same unique bridge B, and both speakers explicitly specify the next segment below it. The example is excluded from the pilot.

{
  "DEMO_ONLY_NOT_A_PILOT_CASE": {
    "review_status": "reviewed",
    "reviewer_id": "r_demo",
    "prefix_first_review_completed": true,
    "assistant_draft_seen_before_judgment": false,
    "focal_pair": [
      "giver",
      "follower"
    ],
    "local_question": "On which side of bridge B should the next route segment pass?",
    "focus_source_ids": [
      "DEMO.row.001",
      "DEMO.row.002"
    ],
    "participant_meanings_with_source_quotes": [
      {
        "participant_id": "giver",
        "meaning": "Instructs a below-B next segment.",
        "source_quotes": [
          {
            "source_id": "DEMO.row.001",
            "quote": "The next segment goes below bridge B."
          }
        ]
      },
      {
        "participant_id": "follower",
        "meaning": "Explicitly adopts a below-B next segment.",
        "source_quotes": [
          {
            "source_id": "DEMO.row.002",
            "quote": "I will take the next segment below bridge B."
          }
        ]
      }
    ],
    "task_outputs": {
      "giver": {
        "proposed_output": "Route(next_segment, below, bridge_B)"
      },
      "follower": {
        "proposed_output": "Route(next_segment, below, bridge_B)"
      },
      "conditions": [],
      "status": "consequence of the expressed readings; execution is not observed"
    },
    "blocking_uncertainty": false,
    "provisional_label": "ALIGNED",
    "evidence_verified": true,
    "include_in_pilot": false,
    "inclusion_or_exclusion_reason": "Fictional teaching example; exclude from every real pilot dataset. Verification flags describe the hypothetical completed review only.",
    "later_evidence_review_completed": false
  }
}

For real records, preserve exact quotes, record both participants, and add the actual context/antecedent evidence needed by the interpretation. The optional nested keys participant_id, meaning, source_quotes, proposed_output and conditions are conventions for legible review notes; they do not change the runner’s schema.

7. From this review file to a defensible pilot

StepWhat must actually happen
A. Complete individual reviewsUse a separate file per reviewer. Save the first prefix-based judgments before reading one another’s answers or later outcomes. Record exposure and outstanding source checks.
B. Compare and adjudicateCompare the same focal question/event, source support, outputs and label. Resolve disagreements with reasons and preserve both original records; do not replace originals with a silent consensus.
C. Verify context and selectionHave an independent map reader check the inventories against the original maps, preferably before dialogue screening. Check admitted game settings where used. Then update selection records and the selected case’s study_role=pilot. Keep all review metadata outside observer_input.
D. Prepare final referencesCreate the separate reviewed-reference format required by the README. Carry forward only adjudicated judgments and verified provenance. Candidate-specific model evidence review happens against actual outputs, separately from reference construction.
E. Execute real model requestsRecord actual model/version/settings in run_configuration.json. pilot.py emits requests; you submit each to the chosen model and save raw responses unchanged. One candidate/one hypothesis requires six requests before local F5–F7 processing.
F. Report preserved outputsUse actual external-model pilot runs, adjudicated references, source/group identity and candidate evidence review. Report exclusions, unresolved cases and failures. A syntax check, supplied-record replay or filled review form is not a measured detection result.

focus_source_idsfocal_source_ids. Confirm the same event/question; matching a row ID alone can be ambiguous.

The README’s context review_status=verified refers to a checked inventory. It is different from an individual human review being reviewed and from a final reference being adjudicated. Completing one does not establish the others.

Observer inputs must continue to contain only the permitted overall_task, participants, context_sources and dialogue_prefix fields. Do not add this form, focal highlights, draft labels, later turns or hidden game roles. Selected spans are research annotations, not hints for primary discovery requests.
