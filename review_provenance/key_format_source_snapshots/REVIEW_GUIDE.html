1. Choose the label using the current rule

Label to enterWhen it is justified
ALIGNEDBoth participants’ supported interpretations lead to the same single task consequence, with no uncertainty that could change that conclusion.
POTENTIAL_MISMATCHBoth participants have supported consequences, the sets are nonempty and known, their consequence sets have no common outcome, and no blocking uncertainty remains.
UNRESOLVEDMissing support, unknown required facts, competing interpretations or overlapping sets of possible consequences prevent either determination.
nullNot yet rated. Keep this until you have made a judgment; it is not a fourth research label.

Compare the same local question, event and phase. Equal sets with several outcomes are not a shared single consequence. An unresolved alternative whose known outcome adds nothing to the supported set need not block; an unknown or new outcome can.

Apply Tier S to both readers

Available is not the same as adopted. A landmark on a map shows that it is available. A bare “okay” shows a response. Neither alone establishes the participant’s chosen referent. Look for participant-owned expressed evidence, a grounded reference link or a specific endorsement, and check for corrections or withdrawals.

Read earlier turns: an explicit statement can already support the interpretation even if the final response is brief. Conversely, a question, echo, rejection or quoted claim may leave adoption unresolved. In Werewolf, annotate public expressed interpretations of claims and operations; do not infer hidden role truth. Keep ambiguous addressees, phases and premise branches visible.

A strict review can conclude UNRESOLVED. Missing evidence is not a reason to invent a reading, force a mismatch or count the case as aligned.

When to enter canonical consequences

Prose is useful for reasoning. For mechanical F7 validation and a determinate adjudicated reference, add task_outputs.supported_consequences, keyed by the two actual participant IDs. Use a predeclared canonical representation so that the same outcome is represented identically.

"supported_consequences": {
  "participant_A": [["route", "event_1", "above", "verified_pine_id"]],
  "participant_B": [["route", "event_1", "above", "verified_pine_id"]]
}

This is a constructed syntax example, not an input to paste into MT03. Replace the keys with the actual pair and enter only outcomes supported by reviewed readings. [] means no supported consequence; null or "UNKNOWN" within an outcome represents an unknown required argument. Do not use a guessed string such as “probably pine” as a known canonical identity. The software never derives semantic equivalence from the prose.

4. Compare readers and complete the pilot

  1. Save the first-pass records. Keep reviewer identities, frozen input hashes and exposures. Calibration on MT03, MT05 and WW02 can help clarify the method; discussed cases are development material unless the evaluation protocol explicitly treats them otherwise.
  2. Compare scope before labels. Are the readers addressing the same event, question, speakers, phase and focus? Inspect supported readings and consequences before resolving the status.
  3. Document adjudication. The comparison script lists differences. The adjudication ledger records the actual resolution, supported readings, exact quotes, consequences, rationale and adjudicator. For a determinate reference, the ledger needs its own participant_meanings_with_source_quotes with supported participant-owned quotations and supported_consequences at its top level. Reader records keep consequences nested under task_outputs. It does not choose a reference for you.
  4. Check context independently. A map reader who has not screened the dialogue should check inventories and correspondences from the images. Record exposure and corrections separately. Confirm game rules and phases; missing media facts remain missing in a text-only condition.
  5. Finalize selection and freeze evidence. A reader’s inclusion recommendation is not the final register. Update accepted cases, context versions and roles only after the required checks. Revalidate and preserve earlier versions.
  6. Run and report the declared model condition. Preserve exact requests, raw responses and failures; score only eligible actual outputs against completed references. Keep assisted-development results separate from independent-reference results.
